# Business Plan Template Refactor Plan

> **Historical — refactor landed 2026-05-13.** This document is preserved as a worked example of how to plan and execute a destructive template refactor inside a memory-based repo workflow. It is no longer the active spec; the active state is the live repository structure plus `doc/DECISIONS.md`. Do not edit this file further. If the template needs to change again, write a new plan rather than amending this one.

## Purpose

Refactor this repository from a human-in-the-loop research coding template into a human-in-the-loop business plan template.

The template should keep the durable project-memory workflow while replacing research, HCC, and biological-analysis assumptions with business-planning assumptions, review gates, and reporting outputs.

This refactor intentionally rewrites `MEMORY.md` and `CLAUDE.md`. The current `CLAUDE.md` instruction that calls `MEMORY.md` "stable" is being superseded as part of this template-level change; both files must be updated together so the new contract is the new stable one.

## Human-In-The-Loop Principles To Preserve

- Keep humans responsible for strategic direction, interpretation, and final business claims.
- Pause for human review before changing core assumptions, positioning, forecasts, market interpretation, pricing, funding asks, or legal/regulatory claims.
- Keep durable project memory in tracked Markdown files so humans and assistants can resume work from the repository itself.
- Keep commits paired with daily log entries whenever possible.
- Keep assistant instructions synchronized across `AGENTS.md`, `CLAUDE.md`, and `.github/copilot-instructions.md`.

## Target Template Scope

The refactored template should support a generic business plan workflow, including:

- business concept definition
- customer and market research
- competitive landscape review
- product or service positioning
- business model and pricing assumptions
- go-to-market planning
- financial-model notes and assumptions
- pitch deck or business-plan presentation output
- human review and decision tracking

## Reporting Workflow

Reporting uses the HTML-PPT Claude Code skill. The template assumes the skill is already installed at the Claude Code user level; the template does not vendor the skill and does not run an install step. If a user does not have the skill, the README points them at the skill's own install instructions.

- Skill reference: `html-ppt-skill` (available as a Claude Code skill)
- Repository: <https://github.com/lewislulu/html-ppt-skill>

Planned reporting conventions:

- Source decks live in `presentations/` (resolved 2026-05-13). Ship two parallel starter decks: `presentations/investor/` (pitch deck) and `presentations/internal/` (full business plan). They share tokens/themes but have separate narratives.
- Rendered or shareable outputs go in `reports/`.
- Use HTML-PPT templates and layouts rather than authoring slides from scratch.
- Use token-based themes and CSS variables from the skill so the two tracks stay visually consistent.
- Include speaker notes for human review.
- Investor track covers: problem, solution, customer, market, competition, business model, traction, financials, roadmap, risks, ask.
- Internal track covers: assumptions, market research, customer discovery, competitive landscape, business model, financials, roadmap, risks, open questions.
- Record major deck-structure and narrative decisions in `doc/DECISIONS.md`.

## Implementation Order

This is the single canonical ordered list for the refactor. It supersedes the earlier "Directory Migration Steps" and "Suggested Implementation Order" lists. Deletions happen near the end so a halfway-aborted refactor still has both old and new sides on disk.

0. Confirm all open decisions are recorded in `doc/DECISIONS.md`. (Done 2026-05-13 — see "Resolved Decisions" below.)
1. Create new business-planning folders with sibling READMEs: `assets/`, `inputs/`, `models/`, `presentations/investor/`, `presentations/internal/`. Keep existing `reports/` and `cache/`.

3. Rewrite `README.md` for business planning.
4. Rewrite `MEMORY.md` and `CLAUDE.md` together — `CLAUDE.md` must be updated alongside so the new `MEMORY.md` is the new stable contract and future sessions are not told to revert it.

6. Rewrite `doc/ENVIRONMENT.md`, `doc/NEW_PROJECT_CHECKLIST.md`, and `doc/PROJECT_STATUS.md`.
7. Rewrite `scripts/doctor.py` against the business-template checklist below; update `requirements.txt` if doctor takes on new dependencies.
8. Drop the Node dashboard: remove `server.js`, `site/`, `package.json`, `package-lock.json`.
9. Remove research / HCC files and folders listed under "Files And Folders To Remove Or Replace" — human review required before this step (see Human Review Gates).
10. Update `.gitignore` to drop research-specific entries and add business-template entries (`presentations/_build/`, etc.).
11. Run `python3 scripts/doctor.py` and confirm it passes against the Acceptance Criteria.
12. Prune stale project-scoped auto-memory entries under `~/.claude/projects/-Users-jyang21-Documents-projects-busplan/memory/` that reference research/HCC context.
13. Update `doc/PROJECT_STATUS.md`, `doc/DECISIONS.md`, and `doc/WORKLOG.md` to reflect the refactored state.
14. Mark this refactor plan historical (banner at top of the file) but keep it in `doc/` as a worked example.
15. Commit each phase as a separate commit on `main` (resolved 2026-05-13: direct on `main` with staged commits, not a feature branch) and run `python3 scripts/log_commit.py` after each commit.

## Acceptance Criteria

The refactor is done when all of the following are true:

1. `python3 scripts/doctor.py` exits 0 with no failures.
2. All six new `doc/` files exist and are non-empty (more than placeholder front matter).
3. Both `presentations/investor/` and `presentations/internal/` contain a slide-by-slide starter source file (`deck.md` per track) that mirrors the slide list in `doc/PITCH_DECK_PLAN.md` and can be picked up by the `html-ppt-skill` when a user authors a real deck.
4. `grep -r -E 'HCC|Slurm|wright_fisher|genotype|phenotype' .` matches only inside `doc/BUSINESS_PLAN_TEMPLATE_REFACTOR_PLAN.md` and `doc/DECISIONS.md` (historical record).
5. `README.md` renders cleanly and contains every metadata field listed under "README Refactor".
6. `MEMORY.md` and `CLAUDE.md` are mutually consistent — `CLAUDE.md` no longer instructs future sessions to treat `MEMORY.md` as untouchable in a way that contradicts the new contract.
7. `doc/PROJECT_STATUS.md`, `doc/DECISIONS.md`, and `doc/WORKLOG.md` reflect the refactored state, and `doc/DAILY_LOG.md` has entries for each phase commit.
